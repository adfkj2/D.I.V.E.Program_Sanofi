# R41：90.2% 的规则审查与工程交付规划

日期：2026-10-12。范围：只读代码、实验产物、手册及远端分支核验，复跑现有测试与离线审计；不改变算法、模型、数据、答案或判分，不启动付费评测。用户要求先仔细规划，再决定实施。

## 结论

**451/500（90.2%）有可复核的非官方自评依据；目前不能给出“规则审查全部通过”的结论。**

现有结果不是空口宣称，也没有在本次检查中发现按题号填答案的实现。但“运行时不泄漏答案”“缓存能重放”“符合比赛诚信要求”是三个不同判断。手册附录 F.1.4 明确包含“对测试集过拟合调参，缺乏通用设计”；当前公开 Oracle 500 题已被多轮错误分析和策略选择使用，不能重新称为盲测集。需要通用性验证及项目组对该边界的解释。

建议停止以提高这 500 题为主要优化目标，保留 R40 原始证据，先完善合规材料、可独立运行的工程版本和业务任务验证。详细实施方案见 [工程与业务验证计划](../24-engineering-delivery-plan.md)。

## 3. 需要重点解释的实现

### 3.1 文本路由与公开评测集反复使用

[R34 记录](32-r33-error-diagnosis-20261011.md)分析了完整 500 题中的 74 道错误；R36-R40 随后针对时间拒答、建议请求、当前属性等机制迭代。对应运行时读取问题文本、回答状态和证据日期，例如：

- [时间问题复核](../../src/dive_memory/oracle/temporal_refusal_reader.py)
- [建议请求复核](../../src/dive_memory/oracle/advice_refusal_reader.py)
- [当前状态复核](../../src/dive_memory/oracle/current_state_reader.py)

这些规则具有可以解释的通用意图，也没有读取 gold 标签；但其中英语模板、排除项及复核条件是在评测反馈后选择的。需要证明“换一种问法、换一个领域仍成立”，不能只换掉题号或给规则改名。

R40 的 200 题筛选集为 185/200，其余 300 为 266/300。**这 300 题也不是盲测集**：历史全量诊断已经暴露了信息。报告中的 `previously_exposed=false` 只能理解为未在当前筛选清单，不能作为历史未暴露证据。

新的验证集可以补充通用性证据，但不能抹去原 Oracle 集已被用于开发的事实；项目组认定也不能由本项目自行替代。

### 3.2 原文保留与记忆真实性

当前策略保留原句窗口和受限文档；这本身不等于违反“禁止全量历史拼接”。本次对 500 份 trace 的补充统计为：

- 10,960 个摄入 turn 中，9,988 个形成至少一条 memory（91.13%）；这不表示保存了这些 turn 的全部内容。
- reader 可见文本字符数 / 原历史字符数的中位数约 32.62%。可见文本含元数据与重复片段，该数值不是净压缩率。
- 3,948 个完整 turn 的文本在对应 reader 上下文中逐字出现；这不是完整证据覆盖率。
- 按当前 `len(text)//4` 启发式计算，可见上下文上限 5,672，中位数 2,040，低于设定的 6,000 估计预算。

Oracle 本来已剪至证据会话，因此高写入比例不能直接判定无选择性；但它也不能证明具备长期噪声过滤和容量治理。后续应使用独立的长期多会话材料加入无关信息，观察选择性、当前状态、旧版本与遗忘。

`ApproximateTokenCounter` 不是模型真实 tokenizer。6,000 是工程估计预算，不应写成精确模型 token 硬上限；手册并未规定 6,000 这个数值。需要同时报告真实模型 usage 和估计证据预算。

### 3.3 缓存与费用

缓存按端点、模式、完整请求内容取哈希，本轮可以重放策略输出。R40 相对 R39 有 494 条最终 hypothesis 相同、6 条不同；复用相同 hypothesis 的旧判分，没有依据题目“是否答对”选择某个历史答案的证据。

这支持“固定策略下复用相同请求结果”的解释，不支持“500 次全新生成”。当前累计 ¥31.456754 是多轮开发费用，R40 ¥0.276516 是增量费用；两者都不是独立冷启动完整 500 题的成本。全量模型调用次数、生成 token、端到端时间仍需按统一运行口径形成报告，不能直接累加混合阶段计时当作一次实测。

已有事件、版本、来源、生命周期、隔离及测试是有价值的基础。手册明确排除生产级高可用和大规模集群部署，不需要为获得学生项目高分把所有生产 readiness 项都做完。

## 5. 审查后的处理顺序

1. 将本结论和具体路由、开发集暴露情况整理成 mentor 可审阅材料；只准备材料，本轮不发送。
2. 保留 R40 全部结果与失败，停止围绕同一 500 题继续追分。将其定位为历史非官方开发成绩。
3. 提取不依赖历史结果目录的通用运行时；工程重构先用相同请求缓存验证行为是否保持。
4. 在新任务和改写/反事实材料上验证规则通用性、记忆真实性及用户价值；配置冻结后再运行终版 Oracle。
5. 正式分数仍以项目组统一脚本、统一 ref 和指定 judge 为准。若其判分仍为 90.2%，换算是 36.08/40；现在不把该数值记为已获分。

本次没有发现足以认定伪造 JSONL、直接答案泄漏或具体题号硬编码的证据；也没有完成代码原创性、全部第三方许可、所有产物隐私或未来正式 judge 的全面鉴定。保留这些审查边界，不将“未发现”写成“已证明不存在”。
