## 方法与结果

使用独立 SQLite 测试库和开发者编写的项目数据，调用原有 `CompatibleModel → AgentEngine → Assistant` 链路。传输外包一层观测器记录请求哈希、用量与耗时，不改变请求正文或模型响应。测试脚本仅在提案符合预设场景范围后确认，随后检查实际持久化状态；正式用户数据未参与。

请求配置为 `https://api.deepseek.com` / `deepseek-chat`，供应商实际返回的模型名称为 **`deepseek-flash`**。这是运行时观察，不保证供应商别名未来不变。

“重新打开”发生于同一个 Python 进程内，不冒称服务进程重启。本轮没有再次进行网页操作；R47 的浏览器证据仍明确属于协议替身。没有真实用户参与、保留集、独立 judge 或统计可靠性结论，不能把这四个成功场景推广成 Agent 总体准确率或 Oracle 提分。

## 实际暴露的改进点

1. **回答过于技术化。** 模型展示了记忆/任务编号、`completed`、`revision`、`supersedes_id` 等字段。业务判断正确，但日常用户只需要当前决定、进展、下一步和可点开的来源。
2. **重复检索拖慢续接。** 最后一轮在上下文已包含任务和交接的情况下又做两次无结果检索，累计五次模型请求、9.558 秒。应区分记忆事实与项目进度的数据来源，减少重复查询，并验证不会遗漏证据。

以上为本轮发现，尚未调整提示词或产品行为，也没有反复调参后挑选成功样本。本轮没有模型错误、重试或被隐藏的失败样本。准备阶段出现一次文档补丁标题不匹配，未改变文件；修正后才登记计划并发起请求。
