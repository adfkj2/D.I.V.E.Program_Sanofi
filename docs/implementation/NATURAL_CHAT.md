# 自然接话与连续消息

本轮同时升级普通聊天与虚拟空间。人物可以主动追问具体细节、接梗、补充和转接话题；不要求每轮提问，也不通过固定口头禅证明拟真。

## 普通聊天

- 用户消息立即保存；连续补充经过800毫秒静默窗口合并回应。输入框始终可以继续发送，每条记忆授权独立并在发送后复位。
- 一次模型请求生成1至4条有独立语义的消息，合计包含至多一条可选沉默续话；每条经过已有格式清理，不按标点机械拆分，也不逐条调用模型。
- 消息通常间隔1至4秒。当前聊天保持可见、用户没有输入、也没有明确问题等待回答时，最后一条之后20至35秒可再自然补充一次；离开、开始输入或发送新消息会取消这次续话。
- 等待时标题显示“对方正在输入中...”，完成、失败或取消后结束。前端根据服务端批次状态显示，不虚构在线状态。
- 新消息取消旧批次未发内容和迟到结果，已发消息保留；原会话继续接收其已请求的回复。刷新、切换人物和重试不会改变消息归属。

## 批次与接口

`reply_batch`持久保存来源用户消息、人物正文版本、上下文截止序号、已清理分条、下一发布时间、取消代数与状态。公开接口仅返回状态和已发布消息，不泄露未发尾部。

- `POST /api/v1/real-conversations/{id}/turns`：原消息参数与幂等标识，返回202及`{user,batch}`。
- `GET /api/v1/real-conversations/{id}/updates?after_sequence=0&after_revision=0`：增量消息、当前批次及修订号；删除传播时返回重置标记。
- `POST /api/v1/reply-batches/{id}/retry`：只恢复仍有效的失败／中断批次。有生成结果时继续未发内容，否则才重新生成。
- `PUT /api/v1/chat-presence`：只包含会话标识、标签页标识、页面可见与是否输入；不传输私人草稿。
- 原消息列表与同步发送接口保留，由同一批次引擎兼容。

每条消息使用稳定批次与分条身份。只有发布时才写入消息表，因此历史、会话预览和下一轮模型看到的内容一致。格式损坏的协议不会作为人物台词发布；正常旧文本仍可作为单条回复。

所有真实供应商调用继续共用最多两个生成槽位。已发送请求无法无成本撤销；迟到结果不发布，但实际用量仍记录。服务重启停止中断批次，由用户选择重试，不自动产生费用。

## 虚拟空间

同一人物一组消息发完后才换人，组内1至4秒，换人间隔从最后实际发布时间起计算12至25秒。发言者和已发布气泡数分别保存。

本人分身每条先展示至少5秒的可干预草稿。接管立即丢弃该组未发尾部；手动改写保持原样，重新提供至少5秒窗口，发布后交给另一人物。待发尾部不提供给对方。

默认20条限额按实际发布消息计数；一次调用的token只记一次。达到token限额后不再发起调用，已在预算内生成的内容可以在剩余条数内发布。暂停、停止、撤权、角色版本变化和重启清理当前草稿与尾部。虚拟空间不叠加普通聊天的沉默续话。

## 数据与验证边界

数据库升级前备份应用库、记忆库、保留题私有库及头像。历史文字、自定义人物和严格评估门禁保持原样。证据删除同时清理待发内容及回执，人物生成内容不会自动成为用户真实记忆。

开发验证仅使用隔离数据、模拟供应商和本地HTTP契约；真实人物风格仍需用户通过现有聊天入口试聊。没有后台使用用户保存的Key。Windows／安卓打包、签名与Release发布继续暂停。
