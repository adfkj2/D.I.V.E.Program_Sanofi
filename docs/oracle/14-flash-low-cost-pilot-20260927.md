# DeepSeek Flash 首轮低成本实测：花了多少钱，测出了什么

> 后续状态：已按用户要求完成 50 题配对及选定 v3 的完整 500 题测试，见 [完整测试报告](15-flash-full-test-20260927.md)。本文件保留首轮 20 题结果，不覆盖历史数据。

测试日期：2026-09-27。

## 结论

真实 API 已跑通。固定 20 题、相同证据的配对测试中，v2 判对 10 题，v3 判对 11 题。账户显示余额从 ¥19.93 变为 ¥19.84，观察到的差额约 **¥0.09**。

**现在不能宣布 v3 优于 v2，也不建议立刻跑 500 题。** v3 救回两道不可答题，但有两道可答题从对变错；另外一道“新增正确”的偏好题，判分口径存在疑点。去掉这道有争议的题，两版均为 10/19。继续扩大调用之前，应先处理已暴露的证据定位、过度拒答和判分稳定性问题。

所有分数均为 DeepSeek Flash 本地自评，不是项目组官方成绩。此次比较只检验 reader 策略，没有测 ER 相对旧装包方案的真实答题增益，也没有比较不同检索模型。

## 1. 比较条件与可复核性

采用已有固定题单 `eval/reports/oracle-reader-pilot-20.ids`，seed 为 20260924，含 16 道可答、4 道不可答，覆盖六类题型。没有根据本次输出重新挑题。

两臂共同条件：

- 官方 DeepSeek 接口，模型 `deepseek-flash`；运行前官方模型列表确认该 ID 存在。
- 关闭 thinking，temperature=0；reader 输出上限 512 token，judge 上限 128 token。
- 相同本地 BGE-M3 语义写入门，固定 revision `5617a9f61b028005a4858fdac845db406aefb181`，本地 GPU 运行，不收 API 费用。
- 检索 embedding 保持非语义确定性占位，不混入本地语义检索这个实验变量。
- balanced 排名、query_excerpt 文档片段、controlled_supplement 受控补入；top-k=10，reader 可见证据预算 1,500。
- v2 使用 `evidence_first_v2`，v3 使用 `evidence_first`，沿用各自既有拒答/格式重试策略。因此这是整体 reader 策略比较，不是单一句提示词的独立因果实验。
- 参考答案只用于答题后的评估，不进入写入、检索或 reader 请求。

逐题审计结果：20/20 的检索结果、打包结果、模型可见证据相同；无字符启发式超预算；两臂代码快照一致。这里的 1,500 是项目现有近似计数，不是供应商精确 tokenizer 的合规证明。供应商输入 token 还包括问题、指令、输出格式与重试。

原始结果目录：`eval/reports/oracle-flash-pilot-20-20260927/`。

## 3. 五道变化题，具体发生了什么

### 3.1 正确拒答：不再拿纽约的天数回答西雅图

题目 `edced276_abs` 问“夏威夷和西雅图旅行总共多少天”。证据中有夏威夷 10 天、纽约 5 天，没有西雅图的旅行天数。

- v2 回答 15 天，错误地把另一个城市的数字用于求和。
- v3 拒答，符合不可答标注。

这是 v3 真正有价值的变化：要求求和的每个对象都有对应事实，而不只是检到两个有关旅行的数字。

### 3.2 正确拒答：不知道 Tom 的时间，不能判断谁先成为父母

题目 `gpt4_fe651585_abs` 问 Tom 和 Alex 谁先成为父母。证据只提供 Alex 在一月收养孩子。

- v2 回答 Alex，并把“没有 Tom 成为父母的证据”当作 Alex 更早的理由。
- v3 拒答。

两个人的比较需要两个人的时间；缺失记录不等于事件没有发生。

### 3.3 回退：两首歌的副歌都找到了，却选错了作品

题目 `eaca4986` 问“第二首歌的副歌和弦/音符顺序”。

- 标准答案与 v2：`C D E F G A B A G F E D C`。
- v3：`G G G G A G F`，来自另一首歌。

两个序列实际都在同一证据包内。这不是“完全没检到”，也不是拒答阈值问题。两个作品在可见证据中共享会话时间，呈现顺序是相关度顺序，来源 ID 又不能直接表达第几个对话回合。模型需要辨认“第二首”对应哪个原始作品。

应优先补可见的会话/回合顺序和作品所属信息，再做新的配对实验。这里能确认的是作品指代选择错误；尚未通过消融证明缺少回合顺序就是唯一原因，不能把 v2 恰好选对等同于现有表示已经可靠。

### 3.4 回退：最新数量出现了，v3 仍声称数量未提供

题目 `ed4ddc30` 问冰箱当前有多少打鸡蛋，标准答案是 20。

- v2 回答 20 打。
- v3 拒答，两次调用后仍说证据未给出当前数量。

证据包中，较新的助手片段写着 “Wow, 20 dozen eggs is a lot!”；较旧的片段是 30 打。最新数量已经出现，但承载它的是助手对用户数量的复述，原始用户数量句没有在可见包中直接出现。

这暴露出来源与更新语义的衔接问题。下一步应检查用户数量句在哪一步丢失，并优先补回用户原句/邻接回合；不能简单把所有助手复述都提升为用户权威事实，也不能只放松 v3 让它更愿意猜。当前拒答可能同时涉及过度保守和缺失直接来源，需要进一步验证。

### 3.5 有争议的“提升”：偏好题两版答案很接近，judge 一错一对

题目 `d24813b1` 询问同事聚会适合烤什么。参考答案希望利用用户曾成功做过柠檬罂粟籽蛋糕的经验。

- v2 建议柠檬薰衣草磅蛋糕、巧克力曲奇，另提供巧克力焦糖甘纳许蛋糕；judge 判错。
- v3 建议柠檬薰衣草磅蛋糕或巧克力曲奇；judge 判对。

主要差别是 v2 多给了一个备选。judge 的简短 yes/no 没有说明为什么这一差别足以改变正确性。按当前宽松偏好题标准，两个答案可能都被接受，也可能都没有充分体现历史经验；因此这道题需要独立复核。

原始判分保留，不事后手工改写。敏感性分析：若这道题判两版都对或都错，净提升均变为 0；若将其排除，两版均为 10/19。本次“+5 个百分点”不应被用作对外提分结论。

## 4. 实际消耗与省钱方式

| 阶段 | 实际请求数 | 输入 token | 输出 token |
|---|---:|---:|---:|
| v2 reader（含重试） | 23 | 49,885 | 3,923 |
| v3 reader（含重试） | 27 | 60,263 | 3,153 |
| judge | 31 | 5,002 | 217 |
| 合计 | 81 | 115,150 | 7,293 |

官方余额查询：开始 ¥19.93，结束 ¥19.84，显示差额 ¥0.09。余额只显示到分，可能有结算延迟；若同一账户有其它调用，也会影响差额。这是实际余额观察，不是已核验单价推算的精确账单。没有用仓库旧文档里的价格冒充当前价格。

成本控制措施：

1. 只跑固定 20 题，不先跑 500；模型列表与余额检查没有发送额外测试对话。
2. 写入门与证据构建都在本地完成；只把必要的题目/有界证据发给 reader。
3. 相同完整请求持久缓存；同题同答案的 judge 请求复用。39 个有效答案对应 30 个独特 judge 请求，避免 9 次重复判分。
4. 断点恢复另命中之前已完成的 2 个 judge 请求，因此恢复进程共显示 11 次缓存命中。
5. 总请求上限 100，token 预算阈值 350,000；请求前按 UTF-8 字节数加余量保守预留，响应后用供应商用量结算。这是调用与 token 控制，不是精确金额硬封顶。
6. 每次调用前落盘计账，遇到连接/鉴权失败立即停止；不确定是否完成的调用不会自动重发。
7. 保留既有 v2/v3 重试规则，没有为省钱偷偷改变其中一臂。下一步可独立测“拒答重试是否值得”：本轮 v3 27 次 reader 调用，高于 v2 的 23 次，不能因为输出更短就认为它一定更省。

## 5. 本轮发现并修复的评测工具问题

v2 的 `18dcd5a5` 输出格式无效：拒答同时携带答案或引用，违反输出协议。该 trace 的 hypothesis 为 null，旧判分封装对它调用字符串哈希时中断。

已经补上：

- null 且明确为无效输出时，规则判失败，不发送 judge 请求。
- verdict 对 null 有明确绑定哈希；不能把 null 判为正确，也不能接收没有失败标记的空答案。
- 超时/错误回退即使生成了标准拒答文本，也不能给总体正确数加分。
- 增加只判分现有结果的入口，保留原始 reader trace 与生成时快照，另保存评估代码快照。

两组答题没有重跑。首次中断前已有 1 次对 null 的 judge 调用，花费输入 144、输出 7 token，该判分被弃用；这 151 token 仍如实计入总消耗，未隐瞒。其余成功缓存全部复用。

最终离线回归：**502 passed，9 skipped**。新增测试覆盖缓存复用、恢复后上限、请求前预留、失败信息脱敏、失败阻止自动恢复，以及 null/错误回退不能获分。

## 6. 下一步与停止条件

本轮已停止新增付费调用，没有扩大到 50 或 500。理由不是额度不足，而是已有证据显示仍有可答题回退，且微小净收益受 judge 分歧影响。

建议顺序：

1. 零 API 成本检查“第二个/上一个”等问题需要的回合顺序，以及数量更新题的用户原句遗漏；做通用修复，不针对具体答案硬编码。
2. 用现有片段失败例补充邻接展开与来源定位测试；保留相同预算，防止补原句又挤掉其他题型证据。
3. 将拒答重试作为独立成本消融，而不是直接把重试关掉并与本次策略混比。
4. 对偏好题等少量主观判分边界做独立复核；不通过多次同模型打分、挑最好结果来“提分”。
5. 候选方案在小规模配对中保住可答题后，再运行已有的 50 题拒答压力集。该集含全部 30 道不可答题，不代表完整 500 的分布。

正式 `evaluate_qa.py` 与指定 judge 仍缺失，官方成绩保持 `NOT_EVALUATED`。用户在聊天中提供过密钥，未写入代码、报告或缓存；完成当前测试后建议在服务商控制台轮换密钥。
