# Oracle 长文档片段检索与实际阅读预算修复

日期：2026-09-24。状态：**代码与离线测试完成；真实模型准确率未评估**。

## 为什么先做这件事

历史 `all + balanced` 实验将助手交付物的标注证据装包数从 4 提到 51，却将跨会话、时间题的标注证据分别减少 23、25 轮。原做法为一篇文档在检索中占一个候选位，随后仅显示约 1200 字符**前缀**；答案若在文档中后部，文档虽被检中却仍不可见。继续全局放宽文档准入或加大上下文预算，会加重竞争，且不能证明记忆机制有效。

还发现一个独立的预算缺陷：旧 v2/v3 reader 将 `packed.items` 中的**完整**记忆重新渲染成带注释证据。`packing.estimated_tokens` 对截断后的平面文本计数，实际 `reader_context_text` 可重新带入长文档。对历史 D 臂 500 条 trace 的只读审计（同一 `len(text)//4` 启发式）显示，平面文本超 1500 的为 0，实际 reader 上下文超 1500 的为 **381/500**；中位数分别为 1299 与 1855.5。详见 [配对 reader 审计](10-reader-paired-pilot.md)。这不是供应商精确 token，也不能据此修正旧 61.8% 的非官方自评；它说明旧自评并非严格的“1500-token 实际证据块”实验。

## 本次改动

1. **原文仍是唯一正式记忆。** 助手长文档按标题、段落等边界拆成可重建的 SQLite 检索片段，每片保留父记忆 ID、原文字符 `start/end`、来源及有效时间。片段不是独立事实，不参与冲突覆盖。遗忘、硬删除、重建 FTS 索引时同步处理派生片段。
2. **显式检索开关。** `document_chunk` 是新 RRF 通道，默认关闭；`--document-chunk-search all` 才让片段命中帮助其父文档竞争 top-k。`assistant_cued` 只凭问题可见文字触发，但当前通用 answer-kind 识别器在 Oracle 助手题的回顾性审计中只触发 23/56，**尚不推荐用它作唯一候选配置**。不根据题型标签在运行时路由。
3. **按问题选择可见原文。** `--document-selection query_excerpt` 在文档超出字符上限时显示相关的精确原文片段；若检索通道给出了命中片段，优先使用该片段，避免“检索中 A 段、打包展示 B 段”。trace 记录可见字符范围和选择来源。`query_excerpt` 需要带文档字符上限的 `balanced` 策略，配置不符会报错。
4. **预算对实际证据块生效。** 装包时用 reader 将要看到的带注释块计预算，传给 reader 的记忆副本也只含可见原文；原始记忆对象不变。若重新渲染的 reader 上下文与装包文本不一致，运行在答题前失败。供应商真实输入 token 仍含规则、JSON 字段及重试，所以本预算只指证据块，而且计数器仍是近似的。
5. **引用必须来自可见片段。** Provider-backed reader 现在也执行 grounded citation 校验；仅在被截掉的原文中出现的 quote 被标为无效输出，而非算作有据答案。

新运行的 manifest 和逐题 trace 记录 `context_budget_version=reader-visible-evidence-v2`、文档选择和片段检索策略。即使新运行仍选择 `prefix/off`，它与旧 D 臂的实际装包行为也不同；旧报告保留作历史诊断，**不能和新运行直接做单变量准确率归因**。现有普通检索配置、旧 A–H 消融预设与 `prefix/off` 开关的默认值不启用片段通道。

## 零 API 验证顺序

先锁定同一份题目 ID、数据 SHA、模型修订版、写入门、`balanced`、top-k=10 与证据预算 1500，然后分别运行：

| 臂 | 文档展示 | 片段检索 | 要隔离的问题 |
|---|---|---|---|
| N | `prefix` | `off` | **新预算版本内**的基线 |
| E | `query_excerpt` | `off` | 只换展示位置能否救回文档后部答案 |
| EC | `query_excerpt` | `all` | 片段索引能否让原本未进 top-k 的文档被检出 |

三臂都先用确定性 reader，比较 `formed → retrieved → packed`、各题型逐题增减、reader 实际证据块长度、耗时和错误。这里的 gold 标注只在**产物生成后**由覆盖分析器读取，绝不传给写入、检索或打包。覆盖不是正确率；只有三臂在同一个真实 reader、同一个 judge 下做配对答题，才能判断净得分。

本地 BGE-M3 加载已改为优先读取固定 revision 的缓存 snapshot，并传 `local_files_only=True`，缺缓存则明确失败，不隐式联网下载。真正 dense 检索是独立消融，不应与本次文档优化合成一个无法归因的“新版”。

## 已验证与尚未验证

- 单元与接线测试覆盖精确字符回链、文档尾部召回、租户/时间边界、遗忘与重建、实际 reader 证据块预算、不可引用隐藏片段、配置拒绝及只用问题文字路由。
- 片段索引目前落在 Oracle 使用的 **SQLite** 存储；PostgreSQL 后端尚未做对等实现，不能声称两个后端能力一致。已有持久化 SQLite 库升级后需要执行 `reindex_lexical()` 回填旧文档的片段索引。
- `assistant_cued`、片段大小、权重、实际答题收益均未完成独立验证；不能根据 500 题的回顾性标签审计反向手工调出“命中所有助手题”的规则再把同一 500 题当无偏测试集。
- 项目组正式脚本和指定判分模型尚未取得，正式成绩仍为 `NOT_EVALUATED`。
